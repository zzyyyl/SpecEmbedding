## 1. 修改目标与动机

导师意见中有几项不能只靠论文措辞解决：

1. relative 的 antisymmetric pair scorer 需要能够与普通 directed pair scorer 做明确、可复现的受控切换；
2. 训练规模和 seed 变化需要在 checkpoint 中记录实际使用的 query 数量和 cache 协议，避免 5,000-query pilot 与 full-split 结果混淆；
3. 效率意见需要一个固定 warm-up、batch、候选规模和测量批次数可配置的工具，而不是依赖一次性硬编码脚本；
4. 化学案例分析至少需要稳定导出 query、候选身份、base 排名和 reranker 排名，供作者进一步人工核对；代码本身不负责生成未经核验的 fragment 因果解释。

本计划的代码目标是让上述比较“可运行、可记录、可测试”，不是预先证明 relative 优于 pointwise，也不是通过实现新工具制造新的科学结论。

## 2. 当前实现与代码缺口

### 2.1 已有能力

- `RelativeCandidateReranker` 已有 `use_antisymmetric` 开关；为 `True` 时计算 forward-minus-reverse，为 `False` 时使用 directed preference。
- `train_rerank.py` 已有 `--max-train-queries`、`--seed`、`--relation-top-k` 和多项 relative ablation CLI。
- `RerankCacheDataset` 已能按 `max_candidates` 截断候选，默认不会将正例重新插入评价列表。
- `analysis/transfer2026_scholargpt_review/efficiency_breakdown.py` 已能在固定硬件上测量 coarse/relation forward 成本，但候选规模、warm-up 和测量范围写死在脚本调用与历史工件中。
- `tests/test_rerank_core.py` 已覆盖 relative 的置换等变性、反对称构造和部分 ablation shape，但没有覆盖 pair mode 的显式配置闭包或 checkpoint 元数据。

### 2.2 需要补强的代码能力

- `use_antisymmetric` 是布尔语义，checkpoint 中没有一个直观的 `pair_mode` 字段；普通 directed control 容易被误读为另一套模型。
- checkpoint 虽保存 `training_config`，但没有单独记录实际 labeled train query 数、训练 cache 的 `pre_top_k`/forcing 状态和 `train_k`。
- 现有效率脚本不能方便地对同一 checkpoint 比较 $K=40,80,160,256$，也不能统一记录 warm-up、测量批次和 candidate-count。
- 没有只读的 query-level case exporter；人工案例分析需要从 cache 和预测文件手工拼接，容易混淆原始 query index 与 batch 内索引。

## 4. 具体设计

### 4.1 显式 pair mode 与兼容策略

新增 `pair_mode`，取值为：

- `antisymmetric`：计算 $g(\rho_{ij})-g(\rho_{ji})$；
- `directed`：只使用 $g(\rho_{ij})$，作为普通 directed pair control。

兼容规则：

1. 新 checkpoint 写入 `pair_mode` 和既有 `use_antisymmetric`；
2. 加载旧 checkpoint 时若缺少 `pair_mode`，由 `use_antisymmetric` 推断；再缺失时默认 `antisymmetric`；
3. `pair_mode` 为非法值时尽早报错；
4. train CLI 提供 `--pair-mode {antisymmetric,directed}`，旧的 `--antisymmetric-pairs/--no-antisymmetric-pairs` 保留为兼容入口；显式 `--pair-mode` 优先，并将最终模式写入 checkpoint。

该修改只把已有布尔分支变成可审计的模式接口，不声称 directed/antisymmetric 哪一个性能更好。

### 4.2 训练规模与协议元数据

在 `best_reranker.pth` 和 `last_reranker.pth` 中增加轻量 `data_summary`：

- 实际进入训练 dataset 的 labeled query 数；
- 用户请求的 `max_train_queries`；
- 实际 `train_k`；
- train cache 的 `split`、`pre_top_k`、`force_include_positive` 和 cache 版本字段（若存在）；
- 当前最终 `pair_mode`、seed 和 model type 的冗余摘要。

元数据只用于 provenance 和结果分组，不参与模型 forward；不复制私有日志、hostname、绝对路径或 GPU 信息。

### 4.3 候选规模 forward benchmark

新增工具支持：

```bash
python analysis/benchmark_reranker_efficiency.py \
  --cache <test-cache.pt> \
  --checkpoint relative=<relative.pth> \
  --checkpoint pointwise=<pointwise.pth> \
  --candidate-counts 40 80 160 256 \
  --warmup-batches 2 --measure-batches 16 \
  --batch-size 64 --device cuda:0 \
  --output analysis/<run>/efficiency.json
```

输出至少包括 source cache、checkpoint、candidate count、relation top-k、batch size、warm-up/measurement 批次数、模型参数量、每 query 时间、吞吐和 CUDA peak memory。计时排除 DataLoader 和数据读取；若输入不是 CUDA，显存字段为 `null`。工具只产生描述性实现成本数据，不计算 Recall/MRR。

### 4.4 Query-level case exporter

新增工具按指定原始 cache query index 导出 JSON：

- true SMILES、候选 SMILES 和候选身份索引；
- base score/rank 与 reranker score/rank；
- base 和 reranker 的 top-$k$ 候选列表；
- 正例是否自然进入 cache、候选池截断和 checkpoint/model config 摘要。

导出器不推断“哪个 fragment 导致变化”，不修改 cache，不插入正例，也不改变评价指标。后续若要写 chemical case study，作者必须基于该导出和原始谱峰/结构资料人工核验。

## 5. 实验与计算边界

- 是否新增训练实验：否；只修改训练接口和 checkpoint 元数据，不启动大规模训练。
- 是否新增评价运行：否；只提供可配置 benchmark 和案例导出工具，并用 synthetic smoke 验证。
- 是否进行静态/合成测试：是；测试 pair mode、checkpoint 兼容性、候选规模输出格式和案例导出字段。
- 是否修改模型默认行为：否；默认仍为 antisymmetric、rank-free、no-forcing 语义。
- 是否新增外部依赖：否；只使用仓库已有 PyTorch、DataLoader 和标准库。

## 7. 风险、证据边界与待确认事项

- **旧 checkpoint 兼容风险**：任何缺失 `pair_mode` 的 checkpoint 必须保持旧布尔配置语义；加载测试失败时不得继续扩展代码范围。
- **模式解释风险**：`directed` 只是普通 pair scorer 的实现 control，不等于完整 pairwise loss、cycle-free ranking 或 hard-negative 方法。
- **训练规模风险**：`data_summary` 只能说明实际使用的数据量，不能替代 full-split 或 alignment-level 稳定性实验。
- **benchmark 风险**：不同硬件、精度、batch、warm-up 和 cache candidate distribution 会影响 timing；输出必须携带协议字段。
- **案例风险**：导出的排名变化不自动具有化学解释；没有原始峰和结构核验时，不能写成 fragment-level 结论。
- **计划偏离条件**：若需要新增训练、评价、外部 baseline、数据格式或模型结构改动，暂停并将状态改为 `已偏离待确认`。
