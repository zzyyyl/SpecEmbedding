## 1. 修改目标与动机

代码阶段已经将修改意见中不能只靠措辞解决的部分落地为可运行接口和工具，但论文尚未同步说明这些实现能力。本文需要补充足够的实现信息，使方法定义、checkpoint provenance、效率边界和后续案例分析入口与当前代码一致，同时保持方法论文叙事，不把工具开发夸大为新的科学发现。

本轮同步的核心目标是：

1. 明确当前报告的 relative 模型使用 `pair_mode=antisymmetric`，并说明代码同时支持 `directed` 作为受控机制入口；没有运行 directed 训练，因此不新增性能结论。
2. 说明训练 checkpoint 的 `data_summary` 可记录实际 labeled query 数、候选协议、forcing 状态、`train_k`、seed 和模型模式，从而区分 5,000-query pilot 与其它训练规模；该元数据不参与 forward，也不替代规模或稳定性实验。
3. 说明仓库提供候选规模可配置的 forward-only benchmark 和 query-level case exporter；二者是可复现性/后续分析基础设施，不产生新的 Recall/MRR、化学因果解释或部署性能结论。

## 2. 当前证据与问题定位

### 2.1 代码中已核验的实现

- `RelativeCandidateReranker` 接受 `pair_mode`，合法值为 `antisymmetric` 和 `directed`；缺省时由旧的 `use_antisymmetric` 推断，旧 checkpoint 缺字段时保持兼容，默认语义仍为 antisymmetric。
- `SpecEmbedding/utils/rerank.py` 在构建和保存模型配置时写入 `pair_mode`，并保留旧字段兼容逻辑；当前 `params.yaml` 的默认模式为 `antisymmetric`。
- `train_rerank.py` 在 `best_reranker.pth` 和 `last_reranker.pth` 中写入 `data_summary`，包括实际 labeled train query 数、`max_train_queries`、`train_k`、候选 cache 的 split/dataset/candidate/pre-top-k/forcing 摘要、seed、model type 和 pair mode。
- `analysis/benchmark_reranker_efficiency.py` 支持多个 checkpoint、候选规模列表、warm-up、测量批次、batch size、设备和 JSON 输出；计时明确排除 DataLoader 与数据读取，工具不计算 Recall/MRR。
- `analysis/export_rerank_cases.py` 导出原始 query index、候选身份、base/reranker score 与 rank、top-k 和 miss 元数据；代码不执行 fragment attribution 或化学因果解释。
- 代码全量测试当前为 `118 passed, 9 warnings`；定向测试、Ruff、compileall 和合成 smoke 均通过。上述验证证明接口和工具可运行，不证明 directed 性能、真实效率曲线或案例科学结论。

### 2.2 论文中的同步缺口

- 方法公式已经定义 antisymmetric pair preference，但没有说明它对应一个显式可切换的 `pair_mode` 接口，也没有明确当前主结果只报告 antisymmetric 模式。
- 实现细节只写 pilot 使用 5,000 queries，没有说明 checkpoint 现在可以携带实际数据量和 cache 协议摘要。
- 复杂度和 Appendix~C 已有 fixed-hardware forward-only 边界，但没有说明当前仓库提供可配置候选规模的 benchmark；不得因此新增未测量 timing 数字。
- 论文没有说明 query-level 排名案例可以从固定 cache 稳定导出，也没有把该工具误写成化学解释结果。
